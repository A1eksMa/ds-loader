# Contributing

## Scope

`ds-loader` — оркестратор обновления данных для `ds`. Всё, что он делает, выражается
**стадиями** (`src/app/`), которые раннер прогоняет за тик. Сейчас их две — `ingest` и
`publish`.

**Входит:** приём файлов и вызов `ds load` (`ingest`); `ds get` → `data/*.js` +
`manifest.js` для `ds-webui` (`publish`); в будущем — жизненный цикл (`ds archive`), сборка
бандла. Всё — через CLI ядра.

**Не входит:** доступ к БД `ds` напрямую, импорт кода ядра, доменная логика конкретной
предметной области (для неё в конфиге источника есть `prep_cmd` — подключаемый хук).

## Ограничения (как у `ds`)

- Только стандартная библиотека Python `>= 3.9`. `pytest` — только dev.
- Офлайн, без сетевых портов.
- Функциональный стиль: `frozen` dataclass, чистые функции в `src/domain/`, эффекты — за
  портами (`src/ports/`) и в адаптерах (`src/adapters/`). Логика стадий (`src/app/`)
  композирует порты, не трогая I/O напрямую.

## Как добавить стадию

1. `src/app/<stage>.py` — функция `<stage>_stage(ctx: Context) -> StageReport`.
2. Зарегистрировать в `src/app/runner.py :: STAGES` и в `src/config/loader.py :: _KNOWN_STAGES`.
3. Всё внешнее — только через порты из `ctx` (при нужде — новый порт + адаптер + фейк).
4. Тесты в `tests/app/` на фейках.

## Definition of Done

1. `./run_tests.sh` зелёный (Docker, Python 3.9.20).
2. Изменилось наблюдаемое поведение (CLI, формат конфига, раскладка архива, контракт вызова
   `ds`) → обновлён соответствующий файл в `docs/reference/`.
3. Новый порт / стадия → запись в `docs/explanation/stages.md`, при необходимости — ADR.
4. Документация — часть изменения.

## Ветки и релизы

`main` — стабильный код. Релиз — архив `releases/ds-loader-<version>.tar.gz` (код без тестов)
+ пункт в `releases/README.md`.
