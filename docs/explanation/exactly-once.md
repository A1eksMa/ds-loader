# «Загрузить ровно один раз»

## Проблема

Ядро `ds` — append-only и **не идемпотентно**: тот же файл, загруженный дважды, = два
комплекта транзакций в журнале. `ds-loader` обязан это предотвратить.

## Механизм

### 1. Обработка по одному файлу, транзакционно

`ingest` не батчит. Для каждого файла: `ds upload` → запись в журнал → перемещение в архив
(`ds upload`, не `ds load` — приём не доверяет продьюсеру вслепую, см. README.md «Что делает
приём»). Если из очереди упал третий файл — первые два уже полностью завершены (загружены и
перемещены), третий — нет. Следующий проход продолжит с третьего.

### 2. Журнал обработанных (`ledger_path`, JSONL)

Ключ — `<имя файла>:<sha256(содержимого)[:16]>`. Хеш ловит повторную укладку того же
содержимого даже под другим именем.

Порядок в `_process_one`:

```
если ledger.has(key):         # уже грузили
    переместить в архив; выход
если файл ещё дописывается:    # mtime моложе stable_after_seconds
    пропуск до следующего прохода
ds upload ...
если код != 0:                # ошибка ядра (в т.ч. отказ ds upload — новый показатель/тип)
    в карантин + .err; выход
ledger.record(key, ...)       # ← ПЕРЕД перемещением
переместить в архив
```

### 3. Крах-безопасность

| Момент краха | Что при рестарте |
|---|---|
| до `ds upload` | файл на месте, грузится заново — корректно |
| **после `commit` в `ds upload`, до `ledger.record`** | ключа нет → **повторная загрузка → дубль** |
| после `ledger.record`, до перемещения | `ledger.has(key)` → файл просто доносится в архив — корректно |

## Остаточное окно

Строчка между `ds upload` и `ledger.record` — единственное неустранимое окно без помощи
ядра. Оно крошечное (следующая инструкция), но существует.

Пути закрытия (в порядке предпочтения):
1. **`ds load --idempotency-key KEY`** в ядре — записывает ключ, повтор с тем же ключом
   no-op'ит. Не нарушает append-only (это защита на входе). Кандидат в roadmap `ds`
   (`ds upload` того же захочет, раз `ingest` теперь вызывает именно её).
2. **Дублирующиеся по значению транзакции теперь можно чистить постфактум** — `ds compact`
   (см. [`ds/docs/reference/cli.md#ds-compact`](https://github.com/A1eksMa/ds/blob/main/docs/reference/cli.md#ds-compact)),
   уже реализован в ядре. Лечит по факту (после того, как дубль уже случился), а не
   предотвращает — окно этим не закрывается, но ущерб от него обратим.

До этого: окно задокументировано, `ledger.record` идёт первой же операцией после успеха
`ds upload`, а при подозрении на дубль после аварии — ручная проверка журнала `ds` (или
`ds compact --src ... --yes`, если дубль подтвердился).
